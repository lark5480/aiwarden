## 一、三条最重要的结论

### 结论 1：AI 方向「平台层已经挤爆，工程化治理层几乎全空」

Java AI 应用平台的同质化极严重。**多模型接入 + 本地 RAG + MCP + 可视化工作流 + 多智能体**几乎是所有项目抄的同一份清单——RuoYi AI、MaxKB4j、AIFlowy、LangChat、snail-ai、Argus 全是这个配方。

真正没人做的，是下面这六件事：

| # | 治理能力 | 谁做了 | 谁没做 |
|---|---|---|---|
| 1 | 向量库与业务库的**最终一致性**（删文档后向量何时消失） | 无人做完 | **Ragent 作者亲口承认未解决**，方案锁进付费墙；MaxKB4j 双写无补偿 |
| 2 | 权限**下沉到检索层** + 越权测试集 | BizBuddy（单人新项目） | RuoYi AI 官方 FAQ 自认「并非严格意义的 SaaS 多租户」 |
| 3 | RAG/Agent **评测集与 CI 回归门禁** | 无人做完 | Ragent 只有教程章节；编程导航系项目零评测 |
| 4 | Agent 工具调用的**副作用幂等 + Saga 补偿 + HITL** | 各做一半 | Spring AI / LangChain4j **原生无 Checkpoint 无 HITL** |
| 5 | **Token 成本四维归因**（租户/会话/步骤/工具）+ 预算熔断 | 网关只到「请求级」 | 网关看不到 Agent 内部步骤；应用侧熔断依据是健康度不是成本 |
| 6 | Agent 长任务**断点续跑与幂等重放** | 仅 AgentScope-Java（重框架） | Spring AI 2.0 与 LangChain4j 均无 |

**这六件事恰好是 Java 后端的主场**——而本人已有的「分布式一致性实验室」正是这六件事的能力底座。

### 结论 2：最硬的证据来自竞品作者的自我承认

Ragent 作者专文《Ragent 为什么从 Milvus 换成 Pgvector》原文逻辑：

> 删一篇文档要动 `t_knowledge_document`、`t_knowledge_chunk`、`t_knowledge_document_chunk_log`、`t_knowledge_vector` 四张表。Milvus 方案下 `@Transactional` 管不住第 3 步，只能改成 `afterCommit` 异步删 → **产生「脏向量」，下次检索还能捞出来**……**「不管你怎么编排顺序，只要数据分散在两个不参与同一事务的系统里，就必然存在中间状态不一致的窗口。」**

他给出的方案是「本地消息表 + 补偿任务、Seata、定时对账」——然后**这里就是付费墙**。

**他最后选 pgvector，是用「消灭跨库」来规避一致性问题，而不是解决了它。** 这一条比任何「我觉得可以优化」都硬：**竞品作者自己把痛点写出来了。**

### 结论 3：技术栈窗口期 —— Java 21 + Spring Boot 3 反而是稀缺定位

| 框架 / 项目 | 技术栈要求 |
|---|---|
| Spring AI 2.0 | **强制 Spring Boot 4.x / Spring Framework 7 / Jackson 3**，2.0.0-M1 起放弃 Java 17 |
| Spring AI Alibaba | **强绑 Spring Boot 4.x** |
| BizBuddy | Spring Boot 4.1.1 + Java 21 |
| Snailclimb/interview-guide | Spring Boot 4.1 + **Java 25** |

**在「Java 21 + Spring Boot 3」这条线上仍保持活跃的头部项目，事实上只剩 RuoYi AI（SB 3.5.8）、MaxKB4j（SB 3.5）、Ragent（SB 3.5.7）。**

选 Java 21 + SB 3 **不是落后，是对准信创 / 银行 / 国企的存量栈**——MaxKB4j 作者的原话是「让现有 Java 工程师直接读、直接改、直接上线」，且明确说「银行、电力、政务的信创场景，**Python 进不了采购目录**」。

> ⚠️ **本段已被后续裁决推翻，勿引用**：现行底座是 **Spring Boot 4.1.1 + LangChain4j 1.21**（SB 3.5 OSS 已于 2026-06-30 EOL，末版 3.5.16）——见 [06 号清单裁决 3](06-PRD修订裁决清单.md) 与 [PRD §7.2](../PRD.md)。**下列原文保留，以存「当时为什么会这么判断」。**

> ⚠️ **答辩红线**：绝不能说「我用 Spring AI 2.0 + Spring Boot 3」。正确表述是「底座选 **LangChain4j 1.x**（Java 17+，框架中立，不强制 Spring Boot 版本），与 Spring Boot 3.5 无冲突；Spring AI 2.0 已要求 Spring Boot 4，所以在存量栈场景我选择不引入这个约束」。

### 2.2 框架类（**不是竞品，是必须选的底座**）

| 框架 | 最低 Java | 是否依赖 Spring Boot | 多 Agent/A2A | Checkpoint | HITL | 安全沙箱 | 向量库生态 |
|---|---|---|---|---|---|---|---|
| **Spring AI 2.0**（9,508★） | 21+ | **必须 SB4** | ❌ | ❌ | ❌ | ❌ | 20+ |
| **LangChain4j**（13,202★） | **17+** | **可选（框架中立）** | ⚠️ 需组装 | ❌ | ❌ | ❌ | **30+** |
| **AgentScope-Java**（5,868★） | 17+ | 可选 | ✅ 原生 A2A | ✅ | ✅ | ✅ Docker | 中等 |
| **Spring AI Alibaba**（10,957★） | 21+ | **必须 SB4** | ✅（Graph 模拟） | ✅ | ✅ | ❌ | 20+ |
| **Solon AI**（459★） | **8+** | **完全不依赖** | ✅ | ⚠️ 部分 | ⚠️ 部分 | ❌ | 中等 |

**结论**：**底座选 LangChain4j 1.x**——Java 17+、框架中立、与 SB 3.5 零冲突、向量库生态最大。**Spring AI 是「LLM 统一接入 SDK」不是 Agent 编排框架**（官方共识：无 Graph 编排、无 Checkpoint、无 HITL、无沙箱），复杂 Agent 全部要二次开发。

> ⚠️ **该句的版本部分已被 [06 号裁决 3](06-PRD修订裁决清单.md) 推翻**——「与 SB 3.5 零冲突」不再成立：现行底座为 **Spring Boot 4.1.1 + LangChain4j 1.21**（理由见本文件文首说明）。LangChain4j 这个选择本身**未被推翻**。

**关键工程纪律**：**不要在核心业务代码中强依赖特定 AI 框架的 API**——用自研 Java Interface 屏蔽（所有评测文章都强调这一点）。同时把 MCP 当工具标准协议。

| **华为云面试向文章** | 评测样本结构：40 正常 + 20 风险（越权/重复提交/危险描述/工具超时/信息冲突/提示注入），每条含 `expected_text` + `expect.outcome`（deny / human_handoff）+ `forbid_tools` + `max_tickets`，**断言数据库终态** |

### 4.2 需规避

| 规避项 | 原因 |
|---|---|
| **8 个专用线程池** | Ragent 的做法；Java 21 虚拟线程一行配置即可，且更容易讲清楚 |
| **靠「换库」回避一致性问题** | Ragent 从 Milvus 换 pgvector 是把问题藏起来，不是解决 |
| **双写不做补偿/对账** | MaxKB4j 的 `dualWrite` 就是这个缺陷 |
| **做「平台/中台」** | 「个人项目撑不起平台二字」；定位必须是**组件 / 治理层** |
| **摆件式可视化工作流** | 要么不做，要么 8–12 个**每个都能单测**的节点 |
| **前端不开源** | MaxKB4j 的赞助墙做法；求职作品必须全栈开源 |
| **写死向量库** | RuoYi AI 切换向量库需重新导入全部数据 |
| **「XX 如何写简历」式文档目录** | 会立刻被识别为课程作业 |
| **再写一个通用 LLM 网关** | Go 侧 One API(36.6k)/New API(45.7k)/Higress(9.5k) 量级碾压且功能完备 |

### 4.3 待验证 / 方法论提醒
