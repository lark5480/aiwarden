# 选题论证与差异化声明

> **性质说明**：本文档是**开工前的立项调研**（不是完工后的回溯性调研）。
> 姊妹项目 [`mall-consistency-lab`](https://github.com/lark5480/mall-consistency-lab) 的 `docs/ECOSYSTEM.md` 最后一节写过一条方法论沉淀：**「本简报约 30 分钟即可完成，开工前做的成本远低于完工后补做；下一个项目把它作为步骤 0。」** 本文档就是那个「步骤 0」。

## 二、三个候选方向与打分

| 维度（权重） | A. 多租户 AI 应用治理层 | B. AI Agent 执行运行时（持久化执行 + 代码沙箱） | C. 金融账务引擎（复式记账 + 清结算） |
|---|---|---|---|
| 命中 JD 头部趋势（×3） | ✅ 35% 岗位要求 AI | ✅ AI（但更偏 infra） | ❌ 零 AI 关键词 |
| 竞品空白强度（×3） | **✅✅ 竞品作者亲口承认缺口** | ✅ Java 侧空白，但阿里 AgentScope-Java(5.8k)/OpenSandbox(1.5万★) 正在进场 | ✅ 账务内核稀缺（roncoo-pay 停更 3 年） |
| 与已有壁垒的复用度（×3） | **✅✅ 直接复用 Outbox + 幂等消费 + 补偿 + 对账** | ✅ 复用 Saga 补偿 + 状态机 | ✅✅ 复用对账 + 幂等 |
| 广度覆盖（×2） | **12 / 14** | **14 / 14** | 9 / 14 |
| 工程量与踩坑风险（×2） | 中（无容器运行时依赖） | **高**（容器/cgroup/seccomp/durable execution） | 中 |
| 可演示性（×1） | 高（B 端治理台 + C 端问答） | 中（沙箱执行要造场景） | 中（账本报表偏后台） |
| 故事清晰度（×1） | **✅ 一句话说清** | ✅ | ✅ |
| **加权结论** | **✅ 选定** | 备选（工程量最大） | 备选（金融岗专用） |

> ⚠️ **表中数字的来源与效力**：「35% 岗位要求 AI」出自**培训机构来源**的就业报告，属**定性推断、未经独立核验**。按 [PRD §15 文档纪律](../PRD.md)，此类数字**只能在本调研序列内引用并标注来源**，**不得用于 README / 对外材料 / 公开表述**（见 [05 §六](05-独立验证与交叉质询报告.md) 共识第 6 条）。

### 为什么选 A

1. **它的差异化证据最硬，而且是竞品自己写的。** Ragent 作者专文承认「跨库无事务 → 脏向量 → 删除后还能被检索出来，这是很严重的合规问题」，并把解法锁进付费墙。**这是本次调研中唯一一个「由竞品作者公开承认未解决」的缺口。**
2. **它把「AI 项目」重新定义成「分布式数据一致性问题」。** 面试官默认把 AI 项目归类为课程作业；而本项目的核心主张是「大模型有不确定性，但**工具调用的副作用、数据的可见性、成本的上限必须是确定的**」——这句话把项目拉回 Java 后端的主场，是**反击「套壳」质疑最有力的表述**。
3. **它的广度覆盖足够高（12/14）且风险可控**：不需要引入容器运行时/cgroup/seccomp 这类高摩擦基础设施，用 PostgreSQL + pgvector + Kafka + Redis + OTel 即可闭环。
4. **它的定位可以写得很聪明。** 第三方对 RuoYi AI 的评测结论是「5.5k star 的个人项目撑不起『企业级 AI 平台』的『平台』二字」——所以本项目**自称「治理层 / 组件」，不自称「平台」**。组件可以被追问、被验证、被讲边界；平台只能被比功能，而功能必然比输。

### 为什么暂不做 B、C

- **B（Agent 执行运行时）**：广度覆盖最全（14/14），但工程量最大（容器隔离、durable execution 引擎、评测体系同时上），且 **Java 侧窗口正在被阿里系关闭**（AgentScope-Java 5,868★、Spring AI Alibaba 10,957★、OpenSandbox 15,680★）。**其最有价值的部分——「工具调用副作用治理」——已经被 A 吸收进需求。**
- **C（金融账务引擎）**：业务纵深最强、直接命中金融科技方向，但 AI 关键词为零（「35% 岗位明确要求」为**培训机构来源的定性推断**，非独立核验数据），广度覆盖仅 9/14。**建议作为 A 之后的第 11 个项目**，或直接基于现有 `mall-consistency-lab` 的对账能力做增量。

## 三、项目定义

### 3.1 名称与定位

| 项 | 内容 |
|---|---|
| **仓库名** | `aiwarden` |
| **中文名** | AIWarden · 多租户 AI 数据与算力治理层 |
| **一句话定位** | **面向 Java 技术栈企业的 AI 应用治理层**：让「删掉的文档不再被检索到、没有权限的人一条都搜不到、超时重试不会建出第二张工单、每一分 Token 都能归到具体租户和具体步骤、Agent 挂在第 3 步能续上」这五件事，变成**有代码、有测试、有指标、有结论表**的东西。 |
| **定位纪律** | ❌ 不写「平台 / 中台」；✅ 写「治理层 / 组件」。理由见 §4.4 风险 3。 |

### 3.2 五条确定性承诺（产品第一屏就写这五条，而不是技术栈）

| # | 承诺 | 可验证方式 |
|---|---|---|
| **P1** | **删除即失效**：删除一份文档后，它在向量库与全文索引中的一切痕迹在承诺时限内消失 | 对账任务输出「未清理向量数」指标 + 删除后 5 秒的检索断言（自动化用例） |
| **P2** | **检索层隔离**：租户 / 组织 / 知识库 / 文档四级权限在**向量检索前**算成可见集并下推到 metadata filter；越权查询 0 命中 | 20 条越权样本进 CI，断言 `deny` 率 100% |
| **P3** | **副作用幂等**：一次写操作工具带幂等键；失败走**补偿**而不是重试；断网重放不产生第二张工单 | 「模型已决定建单但工具未返回时断网」的故障注入用例 + 数据库终态断言 |
| **P4** | **成本可归因**：Token 与耗时按**租户 / 会话 / Agent 步骤 / 工具**四维归因；超预算先降级再熔断 | Prometheus 指标 + 单测里可注入的预算熔断断言 |
| **P5** | **长任务可续跑**：Agent 执行持久化为状态机，进程重启 / 超时 / 人工中断后从最近检查点续跑，**重放不产生重复副作用** | kill -9 重启后续跑用例 + 副作用计数断言 |

> 这五条分别对应 [`03-竞品调研与饱和度分析.md`](03-竞品调研与饱和度分析.md) §1 表格中的六项治理空白（P2/P3 之间是权限与副作用两件事）。

## 四、差异化声明

### 4.1 「有了 Ragent / RuoYi AI / MaxKB4j，为什么还要这个项目？」

| 问题 | 它们的答案 | 本项目的答案 |
|---|---|---|
| 删文档后向量什么时候消失？ | Ragent：**承认有窗口，方案锁付费墙**；MaxKB4j：双写无补偿 | 事务性发件箱 + 幂等消费 + 补偿任务 + **定时对账输出不一致清单**，一致性延迟有 SLO |
| 谁越权检索到了什么？ | RuoYi AI：**官方 FAQ 自认多租户是假的** | 检索前算可见集 → 下推 metadata filter → **20 条越权样本进 CI 门禁** |
| 重试会不会建两张单？ | Ragent 的 `IdempotentSubmit` 只防表单重复提交 | 工具调用带幂等键 + **补偿日志 + 死信 + 终态可查** |
| Token 花在哪个租户的哪一步？ | 网关只到请求级；应用侧熔断依据是健康度 | **四维归因**（租户/会话/步骤/工具）+ 预算降级链路；语义缓存 key 带租户与可见集 |
| Agent 挂在第 3 步怎么续？ | Spring AI / LangChain4j **原生无 Checkpoint** | 状态机持久化 + 版本 CAS + 断点续跑 + **重放幂等** |
| 改一行 Prompt 会不会变差？ | Ragent 有评测**教程章节**（不是门禁） | **60 条样本（40 正常 + 20 风险）进 `mvn verify`**，模型换版本必须全绿 |

### 4.2 一句话差异化

> **别人在做「AI 能聊天」，本项目在做「AI 的账、AI 的门、AI 的后悔药」——把 AI 的不确定性关进 Java 的确定性里。**
>
> 而这件事的底座，恰好是本人已经做过一遍的东西：`mall-consistency-lab` 的「幂等扣减 → 短事务落单 → 失败补偿 → 定时对账」四段式，**原封不动搬到 AI 数据面上**。

### 4.3 交叉验证：本项目的关键设计在别处的印证

| 本项目设计 | 生态印证 |
|---|---|
| 事务性发件箱 + 补偿 + 对账治理「脏向量」 | Ragent 作者给出的候选方案正是「本地消息表 + 补偿任务、Seata、定时对账」（只是他没做完） |
| 权限下沉到检索层 | 公开文章原话：「**在 Prompt 里加『你是安全的助手』毫无意义**，真正的权限控制必须在检索前或路由层完成」「数据过滤必须下沉到存储层」 |
| 工具调用副作用走补偿而非重试 | 华为云面试向文章给出的验收标准：「在模型已决定创建工单、工具尚未返回时断网，**验证重试是否重复建单**」 |
| 60 条样本 CI 门禁 | 同文给出样本结构：40 正常 + 20 风险，含 `expect.outcome` / `forbid_tools` / `max_tickets`，**断言数据库终态** |
| 引用「状态版本 CAS 与实例复用冲突」作为难点 | BizBuddy 公开的坑：`AgentState` 版本化 CAS，复用旧实例会反序列化失败——**证明这个难点是真的** |
| 虚拟线程 + `ReentrantLock` 避 pinning | MaxKB4j 的实践与作者推理（JDK 21 上 `synchronized` 会 pin 载体线程，JDK 24 JEP 491 才解决） |

### 4.4 风险与对策（写在开工前，避免中途自欺）

| # | 风险 | 对策 |
|---|---|---|
| 1 | **AI 项目被默认归类为课程作业**（华为云文章标题即结论：「不是大模型不新，而是项目只证明接口调通了」） | 项目第一句写**业务承诺**不写技术栈；README 第一屏是五条确定性承诺 + **结论表**（通过率/拦截率/重复建单数/P95/单次成本），不是技术栈徽章 |
| 2 | **正面竞争打不赢教程项目**（Ragent 3k~4.2k★ 绑定课程与知识星球；yu-ai-agent 2,714★ README 直写「增加简历竞争力」） | 不追功能覆盖面，只做它们**全部缺失的那一列**；证据做成「面试官能追问的东西」（测试、指标、报告），不做截图 |
| 3 | **「个人项目撑不起平台二字」** | 自称**治理层/组件**，不自称平台；竞争对象是**一条痛点**（Java 团队被迫用 Python 的痛苦 / 教程项目不敢碰的治理问题），不是一个功能清单 |
| 4 | **技术栈版本说错一句话就被击穿** | 底座 = **LangChain4j 1.x**（Java 17+、框架中立、与 SB 3.5 零冲突）；**绝不写「Spring AI 2.0 + Spring Boot 3」**；答辩时主动讲清为什么不用 Spring AI 2.0（它要求 SB4）。⚠️ **本行的版本口径已被 [06 号裁决 3](06-PRD修订裁决清单.md) 推翻**：现行底座为 **Spring Boot 4.1.1 + LangChain4j 1.21**，且**不得再说 SB 3.5**（已 EOL） |
| 5 | **技术事实被二手摘要污染** | 所有技术事实以官方文档为准；README 里每个版本号都能在 `pom.xml` 找到 |
| 6 | **五条承诺做不完** | PRD 按 M1–M4 分期，**每一期结束都能独立写进简历**（见 PRD §8 里程碑） |

### 4.5 Roadmap 过滤器（只吸收强化定位的东西）

按「是否强化『确定性治理层』定位」筛选：

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P0 必做** | P1 删除即失效（Outbox + 补偿 + 对账） | **唯一一个竞品作者公开承认未解决的缺口**，定位最强 |
| **P0 必做** | P2 检索层权限 + 越权 CI 门禁 | 竞品自认做不到；且是本人现成能力 |
| **P0 必做** | P3 工具副作用幂等 + 补偿 | 最能反击「套壳」质疑 |
| **P1 应做** | P4 成本四维归因 + 预算熔断 | 通用后端能力（配额/限流/降级/归因）在 AI 场景的落地 |
| **P1 应做** | 评测集进 CI（40 正常 + 20 风险） | 「可验证交付」的直接证明 |
| **P2 可做** | P5 断点续跑（状态机 + 版本 CAS） | 难度中高，但 BizBuddy 的坑证明它是真难点 |
| **P2 可做** | 自定义 Span 全链路追踪（含虚拟线程 + TTL 的坑） | 可观测性纵向升级；见效快 |
| **不做** | 多模态、语音、绘画、短剧、小程序 | 摊薄精力，与定位无关 |
| **不做** | 可视化工作流画布（20+ 节点） | 摆件式工作流是重灾区；改为 **8–12 个可单测的确定性节点** |
| **不做** | 再写一个通用 LLM 网关 | Go 侧三个量级碾压者，功能已完备 |
| **不做** | 前端做六个仓库 | RuoYi AI 的反面教材 |

## 五、这个项目不需要重新学的东西

| 已有能力 | 在本项目中的新用途 |
|---|---|
| `mall-consistency-lab` 的事务性发件箱 + 幂等消费 + 补偿 + 定时对账 | **直接成为 P1/P3 的核心骨架**——把「扣库存」换成「删向量」和「调工具」 |
| `aurora-admin` 的 Outbox + RabbitMQ DLQ + 补偿任务 | 同上，且是本项目 Kafka 消费端的设计参照 |
| `hospital-system` 的 DDD 分层 + ArchUnit + 审计 AOP + JSONB | 模块结构与「谁做了什么」的审计留痕 |
| `flash-sale` 的 Lua 限流 + 多级缓存 + Micrometer 自定义指标 | P4 的配额熔断与指标面板 |
| `inkwell` 的 JPA Criteria 动态查询 + Redis 计数缓冲 | 管理台多条件查询与用量缓冲写入 |
| `aurora-admin` 的 `@DataScope` SQL 改写 | **P2 权限下推的直接前身**——从改写 SQL 变成改写向量检索 filter |

**结论：本项目的技术难点是新的（向量一致性、检索层权限、Tool 副作用、Token 归因、Checkpoint），但解题方法论是旧的（Outbox / 幂等 / 补偿 / 对账 / 状态机 / 配额）。这正是「补广度但不丢深度」的最优形态。**
