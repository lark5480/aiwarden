## 一、背景与方法

第一组调研与 PRD（2026-10）给出了选题、竞品与技术选型的完整论证。为避免「自己论证自己批准」，第二组以独立视角重跑关键结论：3 名调研员分别从**文档审查**（论证链条是否有硬伤）、**竞品调研**（赛道饱和度与证据真实性）、**资产盘点与缺口**（命中率与候选对比）三个切入面重新取证，再经 3 轮交叉质询收敛。

方法为四步闭环：**分头调研 → 互授结论 → 反驳补充 → 事实核验收口**。

- **第 1 轮**：三方独立产出结论与反驳清单（互不先通气）；
- **第 2 轮**：互授结论后交叉质询，暴露分歧、各自表态与修正；
- **第 3 轮**：对仍存分歧的命题做一手事实核验（官方文档 / 官方漏洞库 / GitHub Releases 直抓），裁决收口。

所有被推翻或需校准的表述均已落入 [06 号文档](06-PRD修订裁决清单.md)的修订动作；本文档只记录过程与证据。

## 二、三方第一轮结论摘要

### R1（Alex · 文档审查）

PRD 的论证链条**大体成立**：复用「一致性 / 幂等 / 对账 / 故障注入」这套既有武器（01 §四）、竞争「一条痛点」而非功能清单（04 §4.4）、诚实纪律（PRD §12「没做的写待验证」）三条主线都立得住。但存在**四处硬伤**：

1. **SB 3.5 版本红线自击**：PRD §7.1 选 Spring Boot 3.5.x，而 SB 3.5 的 OSS 支持已于 2026-06-30 EOL——一个把「版本红线」写进 §7.2 的项目，自己的底座踩在断供线上；
2. **内部矛盾**：§7.1 写「gRPC 内部检索/摄入服务间调用」，§10 又明确「采用模块化单体（不做微服务拆分）」——单体内部引入 gRPC 是自相矛盾的选型；
3. **「算力治理」名不副实**：标题与 §14.1 自称「算力治理层」，实际治理对象是 Token / 请求 / 存储用量，不碰 GPU 算力，术语会被面试官一击即溃；
4. **「六项治理空白几乎全空」表述需校准**：Spring AI 2.0 已于 2026-06-12 GA，其挂点（ToolCallingAdvisor：工具循环可拦截、可组合、支持流式）已就绪，治理**实现**仍空白、Checkpoint/HITL 在 Spring AI 无原生能力（Checkpoint 是 LangGraph 概念）——「空白」依然成立，但「几乎全空」必须收窄到「治理实现」层面。

### R2（Sam · 竞品调研）

赛道呈**哑铃型**：一头是中转红海饱和——One API 维护放缓、New API（40k+ star、周更）仍有配额计费级 CVE、LiteLLM（53k+）以企业版锁定审计功能；另一头是企业级治理层存在**实锤缝隙**（配额一致性、审计、租户隔离），且 Java 生态结构性空位——头部治理类项目全是 Go/TS/Python。同时必须正视反向证据：同类开源弃坑率高（BricksLLM / Glide / Veloera / Helicone 进入 maintenance mode）、New API 作者年投入近 10 万元仍难以为继、中转站赛道有黑灰产污名。结论：需求真实，但「独立治理产品」的生存模型不成立，适合**寄生在应用里的治理组件**形态。

### R3（Tina · 资产盘点与缺口）

10 个存量项目已覆盖微服务 / 一致性 / MQ / Redis / ES / 测试 / 架构治理（01 号文档矩阵）；2026 市场最大且被真实 JD 验证的缺口是 **AI 应用工程化**，其次是 Kafka / K8s / OTel Trace / 虚拟线程 / 多租户（02 号文档 T1–T7）。按 13 项缺口矩阵重算：aiwarden **全量口径命中 8/13、裁剪口径 6/13**，仍显著高于候选 B（Agent 运行时：命中相当但工程量 2–3 倍）、C（金融账务：3–4/13，留作第二项目储备）、D（Flink 管道：3–4/13，不建议，与求职方向错位）。裁剪损失的「分库分表 / K8s」覆盖只能靠存量项目背书，是真实损失，不做掩饰。

### 3.2 三次立场修正（本轮质询的实质产出）

**修正① R2 撤回「Java AI 治理网关」定位，统一为「数据面治理组件」。**
第 1 轮 Sam 以「New API 配额 CVE + LiteLLM 企业版锁审计」论证 Java 侧治理网关机会；第 2 轮被 R1/R3 联合反驳后撤回。关键论据是**竞品密度的数学差异**：网关赛道已挤满头部竞品（One API / New API / Higress / LiteLLM），留给新项目只剩语言维度一条缝；而「治理组件」的空白密度完全不同——配额强一致、不可变审计、步骤级归因在 Java 侧几乎无人做。CVE 证明的是**需求存在**，不是**个人项目能赢这个生态位**。统一后的简历一句话见共识清单第 1 条。

**修正② R1 从「P4 全后置」修正为「拆 P4a 前移 / P4b 后置」。**
Alex 第 1 轮把整个 P4 放在 M3（MVP 之后）；接受 Sam 的 New API CVE 证据强度后修正：**P4a**（计量事件 + 四维归因 + 配额检查 + 审计留痕）前移进 M1/M2——计量事件与 P1 的 Outbox 事件共用同一套 Kafka / 消费 / 落库骨架，边际成本极低，拖到 M3 反而要二次改造；**P4b**（四级预算降级链 + 语义缓存）维持后置或砍——个人项目降级链两档足矣（配额检查 → 超限 429 / 小模型），四级链是平台化堆砌。砍 ShardingSphere 分片（FR-COST-06）与语义缓存（FR-RET-04）的结论不变：CVE 证明的是配额逻辑要写对，不是调用明细表真有需要分片的数据量。

**修正③ R3 命中率口径修正 + SB 版本立场被第 3 轮证据反转。**
其一，Tina 接受按 Alex 裁剪清单重算：ShardingSphere（−1）、K8s（−0.5）后，8/13 → **裁剪口径 6/13**，排序结论不变（仍显著高于 C/D，B 工程量 2–3 倍性价比仍差）；同时重申 **OTel 不可砍**——P4 四维归因中「Agent 步骤」维度依赖 Trace span 上下文传播（FR-COST-01），砍 OTel 等于退化到请求级归因、与竞品差距归零。其二，Tina 第 2 轮原立场是「SB 3.5 EOL 不应推导出升 SB4，应转化为选型论证素材（ADR 主题：明知 EOL 仍选 3.5）」；该立场被第 3 轮一手证据**反转**（见 3.3），接受 SB 4.1，ADR 主题反转为「选 SB 4.1 的三条依据 + Jackson 2/3 共存策略」。

### 3.3 第 3 轮事实核验收口（R2 Sam · 一手核验）

针对第 2 轮残留的「SB 3.5 + ADR vs SB 4.1」分歧，Sam 直抓 LangChain4j 官方 GitHub Releases 与 endoflife.date 完成裁决：

- **LangChain4j 对 SB4 已是官方一等公民**：1.13.0（2026-04）适配 SB4，设独立 `langchain4j-*-spring-boot4-starter` artifact 线（早于 Spring AI 2.0 GA 的 2026-06-12）；1.20.0（2026-09-04）提供官方 **Jackson 3 opt-in 模块 `langchain4j-jackson3`**（加依赖即全库切 Jackson 3，删依赖回退 Jackson 2）——「Jackson 3 迁移断裂」的反方前提失效；1.19.0 MCP client 对齐 2026-07-28 规范并新增 agentic 级 tool actions compensation（#5823）；1.21.0（2026-10-02）仍在修复 Streamable HTTP 细节（#6291），主线无停滞。
- **版本警示（一手）**：1.19.1 被官方标记 "published in error, do not use"；新项目用 1.20.0+（推荐 1.21.0）。
- **EOL 数据**：SB 3.5 OSS 支持止于 2026-06-30（末版 3.5.16，官方口径「建议迁移 4.x」）；**4.0 OSS 也将于 2026-12-31 到线，升级目标必须锁 4.1**（OSS 至 2027-07-31）；3.5 断供线后 158 条 advisory 中 96 条（61%）无 OSS 修复版——「3.5 + ADR」叙事难以自圆其说。

**裁决：SB 4.1 + LangChain4j 1.20+（推荐 1.21.0）+ spring-boot4-starter artifact 线**。PRD §7.2 版本红线的前提（「LangChain4j 1.x + SB 3.x 零冲突」）在 2026-04 后已失效，随裁决同步反转，详见共识清单第 3 条与 [06 号文档裁决 3](06-PRD修订裁决清单.md)。

## 五、最终共识清单（13 条）

> 逐条完整转录；每条的【理由】与【落到 PRD 的动作】（含章节号 / FR 编号）见 [06-PRD修订裁决清单.md](06-PRD修订裁决清单.md)。

1. **定位**：保持「多租户 AI 数据与用量治理层」，形态为**数据面治理组件**（ModelClient / VectorStore / ToolExecutor 三条 SPI 边界上做治理），可选 openai-compatible 轻量代理端点作旁路演示；不做网关、不自称平台；简历一句话：「面向 Java 技术栈的 AI 应用数据面治理组件——把数据一致性、检索权限、副作用、用量配额四类不确定性关进确定性里」。
2. **命名**：去「算力」改「用量」；降级链表述为「租户预算决定推理档位」，不叫优先级调度；README 全文禁止出现中转 / 聚合 / Key 池 / 计费转售等中转站元素，演示数据全部虚构企业场景。
3. **版本选型**：SB 4.1（OSS 支持至 2027-07-31，勿选 4.0——2026-12-31 EOL）+ LangChain4j 1.20+（推荐 1.21.0，避开 1.19.1）+ spring-boot4-starter artifact 线；新增 ADR-001「选 SB 4.1 的三条依据 + Jackson 2/3 共存策略（langchain4j-jackson3 opt-in + spring.jackson.use-jackson-2-defaults 回退）」，ADR 验证步骤含 `mvn dependency:get -Dartifact=dev.langchain4j:langchain4j-spring-boot4-starter` 检查；同步修订版本红线表述。
4. **范围裁剪**：砍三档隔离（留行级单档实现 + 三档对比降为设计文档）；砍 ShardingSphere 分片（FR-COST-06）与 gRPC 内部调用（内部矛盾）；砍语义缓存（FR-RET-04）；K8s/Helm/HPA 降为可选里程碑 M4 实验；HITL 三态降为「工具级二态审批开关」（保留与 MCP require_approval / LiteLLM 同名语义的生态对话能力）；B 端 7 页砍到 3 页（一致性报告 / 用量 / 评测表）；评测 60→20–30 条。**OTel 显式豁免不可砍**（P4 四维归因的「Agent 步骤」维度依赖 Trace span 上下文，砍 OTel 等于退化到请求级归因、与竞品差距归零）。
5. **P4 拆分**：P4a（计量事件 + 四维归因 + 配额检查 + 审计留痕）前移进 M1/M2（与 P1 Outbox 共用 Kafka / 消费 / 落库骨架，边际成本低）；P4b（四级预算降级链 + 语义缓存）后置 M3 或砍，降级链两档足矣（配额检查 → 超限 429 / 小模型）。差异化主卖点 = 租户级配额强一致（预扣减 / 幂等 / 对账）+ 不可变审计日志，引用 New API GO-2026-6242/6243 与 issue #5290/#5441 作问题真实性证据（必须带编号引用）。
6. **证据与话术纪律**（新增「文档纪律」节）：简历 / README / 面试话术禁用培训机构数字（「35% 岗位要求 AI」等一律不得出现，改用「AI 工程化是 Java 后端 JD 中增速最快的要求方向（定性）」）；竞品 star 数一律带时点与来源且简历 / README 不写竞品 star；RuoYi-AI 表述降级改写；MaxKB4j dualWrite 移出证据池；Ragent 付费墙可作支柱论据。
7. **技术选型补充**：虚拟线程 WebMVC（`spring.threads.virtual.enabled=true`）成文 ADR-002（理由：用户技能匹配、LLM 长阻塞 IO 场景标准答案、SSE 复用 hospital / inkwell 经验、「评估过 WebFlux 并放弃」叙事价值）；MCP 最小版纳入（≤5 天：1–2 个内置工具以 MCP Server 暴露 + FR-TOOL-05 归一化，复用 P3 幂等 / 审计 / 预算管道，传输用 StreamableHttpMcpTransport，注意 Streamable HTTP 无全局 SSE 流的审计细节），超预算降 roadmap。
8. **演示场景**：AI Agent 自动建工单（断网重放后工单数 == 1 终态断言）；退款单不做（资金语义自挖坑），README 写「同一套幂等 / 补偿机制适用于退款等资金操作，工单是零资金风险的演示替身」。把退款式对账过程（补偿任务扫出脏数据并自动修复）做成演示主角 / 录屏。
9. **边界声明**（README 第一屏新增两条）：治理数据面、不承诺检索质量（召回率 / 引用准确率）；一致性是有 SLO 的可对账，不是绝对一致。
10. **多租户话术降级**：简历表述用「租户隔离机制与跨租户越权自动化验证」（20 条越权样本进 CI、拦截率 100%），不用「多租户治理」大词。
11. **排期修订**（按用户确认：每周业余 10–14h、无硬投递节点）：中枢 10 周、风险预案 14 周；Kafka → Redis Streams 决策点固定第 4 周末；评测 Mock / 录制回放双轨工作量补进清单（flaky 修复常占评测开发 30–50%）；「替换精选作品 Chess Arena」以 MVP 验收达成触发，不按日历周（原排期「第 9 周替换」的日历周表述需修订）。
