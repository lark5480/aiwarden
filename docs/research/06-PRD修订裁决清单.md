## 1. 定位：治理层 → 数据面治理组件（不称网关、不称平台）

**【裁决】** 保持「多租户 AI 数据与用量治理层」定位，形态为**数据面治理组件**：在 ModelClient / VectorStore / ToolExecutor 三条 SPI 边界上做治理；可选暴露一个 openai-compatible 轻量代理端点作为独立部署的旁路演示。不做网关、不自称平台。简历一句话：「面向 Java 技术栈的 AI 应用数据面治理组件——把数据一致性、检索权限、副作用、用量配额四类不确定性关进确定性里」。

**【理由】** 「网关」一词激活多模型接入 / 协议转换 / Key 池等门票功能预期，全是 Go/Envoy 主场（R1）；竞品密度的数学差异：网关赛道挤满头部竞品只剩语言维度一条缝，治理组件空白密度完全不同（R2 撤回网关定位的依据）；在网关比较框架里全输、在治理比较框架里全赢（R3）。组件寄生于应用，不背网关功能包袱，个人维护负担可控。

**【落到 PRD 的动作】**
- 标题与 §1.1：「算力治理层」→「用量治理层」，定位句补「数据面治理组件」表述；
- §1.4 非目标第一条「不做通用 LLM 网关」保留，补一句「也不做网关形态的治理产品」；
- §7.3 `aiwarden-core` 的 SPI（ModelClient / VectorStore / ToolExecutor / TenantResolver）升级为治理边界的正式定义：治理动作必须挂在 SPI 切面上，不侵入业务模块（与 §7.3 ArchUnit 规则 2「业务模块不得直接 import dev.langchain4j.*」互相支撑）；
- **新增**：openai-compatible 轻量代理端点（旁路演示用，非主形态）写入 §10 In Scope 可选项。

## 2. 命名：去「算力」改「用量」

**【裁决】** 全部对外表述去「算力」改「用量」；降级链表述为「租户预算决定推理档位」，不叫「优先级调度」；README 全文禁止出现中转 / 聚合 / Key 池 / 计费转售等中转站元素，演示数据全部虚构企业场景。

**【理由】** 治理对象是 Token / 请求 / 存储用量，不碰 GPU 算力，「算力」会被面试官一击即溃（R1）；「优先级」暗示抢占 / 排队调度，个人项目没有该实现，同样会被追问（R3）；中转站元素与黑灰产强关联，一张截图就能毁掉「企业治理」叙事（R2 反向证据 + R1 执行红线）。

**【落到 PRD 的动作】**
- PRD 标题、§14.1 项目条目「多租户 AI 数据与算力治理层」→「多租户 AI 数据与用量治理层」；
- §3 P4 承诺与 FR-COST-03「预算降级链」表述改写为「租户预算决定推理档位（配额检查 → 超限 429 / 小模型）」，删除「优先级」类措辞；
- §14.2 第 4 条要点同步改写；
- **新增**：README 禁词清单（中转 / 聚合 / Key 池 / 计费转售 / 多渠道分发），并入第 6 条的「文档纪律」节。

## 3. 版本选型：SB 4.1 + LangChain4j 1.20+（版本红线反转）

**【裁决】** SB 4.1（OSS 支持至 2027-07-31；**勿选 4.0**——其 OSS 支持也将于 2026-12-31 EOL）+ LangChain4j 1.20+（推荐 1.21.0，避开官方标记 do not use 的 1.19.1）+ `langchain4j-*-spring-boot4-starter` artifact 线。新增 ADR-001，并同步反转 §7.2 版本红线的表述方向。

**【理由】** 第 3 轮一手核验（05 §3.3 / §四）：LangChain4j 自 1.13.0（2026-04）官方适配 SB4 并设独立 starter 线，1.20.0 提供 Jackson 3 opt-in 模块——「迁移断裂」反方前提失效；SB 3.5 OSS 已于 2026-06-30 EOL，断供线后 61% advisory 无 OSS 修复版，「明知 EOL 仍选 3.5 + ADR」叙事难以自圆其说（R3 原立场被证据反转，接受裁决）。

**【落到 PRD 的动作】**
- §7.1 框架行：Spring Boot 3.5.x → **4.1.x**（理由列改写：Spring AI 2.0 生态与 LangChain4j SB4 线均已就位，选 EOL 底座反成红线）；
- §7.1 AI 层行：LangChain4j 1.x → **1.20+（推荐 1.21.0，避开 1.19.1）**，注明使用 spring-boot4-starter artifact 线；
- §7.2 版本红线**整节重写**（而非局部改词）：红线从「不得说 Spring AI 2.0 + SB 3」反转为「底座 = LangChain4j 1.20+ / SB 4.1 / spring-boot4-starter；不得说 SB 3.5（EOL）或 SB 4.0（2026-12-31 EOL）」；
- §14.1 技术栈行同步（Spring Boot 4.1 / LangChain4j 1.21）；
- **新增 ADR-001**（落点为项目开工后创建的 `docs/DECISIONS.md`）：「选 SB 4.1 的三条依据（LangChain4j 官方 SB4 starter 线 + Jackson 3 opt-in + 3.5 EOL 数据留档）+ Jackson 2/3 共存策略（`langchain4j-jackson3` opt-in + `spring.jackson.use-jackson-2-defaults=true` 回退）」；ADR 验证步骤含 `mvn dependency:get -Dartifact=dev.langchain4j:langchain4j-spring-boot4-starter` 检查（闭环 05 §六遗留项 1）。

## 5. P4 拆分：P4a 前移、P4b 后置，主卖点 = 配额强一致 + 不可变审计

**【裁决】** P4a（计量事件 + 四维归因 + 配额检查 + 审计留痕）前移进 M1/M2，与 P1 Outbox 共用 Kafka / 消费 / 落库骨架（边际成本低）；P4b（四级预算降级链 + 语义缓存）后置 M3 或砍，降级链两档足矣（配额检查 → 超限 429 / 小模型）。差异化主卖点 = **租户级配额强一致（预扣减 / 幂等 / 对账）+ 不可变审计日志**，引用 New API GO-2026-6242/6243 与 issue #5290/#5441 作问题真实性证据（必须带编号引用）。

**【理由】** New API 的配额 CVE（GO-2026-6242/6243：整数溢出致负数自增额度、Redis 配额缓存覆盖绕过）与 issue #5290「quota 连预扣缓冲都没有」、#5441 部分模型 0 元购，证明配额一致性连 40k+ star 成熟项目都会栽——比面试向文章硬一个量级（R2 第 2 轮证据，R1 接受）；配额预扣减（Redis Lua）+ 幂等 + 对账是用户从「秒杀库存预扣」平移成本最低的能力（R1）。

**【落到 PRD 的动作】**
- §3 P4 承诺拆为 P4a（M1/M2 交付：四维归因 + 配额检查 + 审计留痕）与 P4b（M3 可选：降级链 / 语义缓存）两段表述；
- FR-COST-01/02 归入 P4a 随 M1/M2 交付；FR-COST-03 重写为两档降级（原四级链与语义缓存引用移除）；FR-COST-07 租户限流保留；

## 7. 技术选型补充：虚拟线程 WebMVC（ADR-002）+ MCP 最小版

**【裁决】** 虚拟线程 WebMVC（`spring.threads.virtual.enabled=true`）成文 ADR-002；MCP 最小版纳入（≤5 天：1–2 个内置工具以 MCP Server 暴露 + FR-TOOL-05 归一化，复用 P3 幂等 / 审计 / 预算管道，传输用 StreamableHttpMcpTransport），超预算降 roadmap。

**【理由】** 用户技能匹配（无 WebFlux/Reactor 关键词）、LLM 长阻塞 IO 场景的标准答案、SSE 复用 hospital / inkwell 经验、「评估过 WebFlux 并放弃」的选型叙事本身有价值（R1/R3 一致）；MCP 挂 P3 同一挂点即「调用前检查」，独立做即重复建设（R3 依附原则 + R1 adapter 顺序）；注意 Streamable HTTP 无全局 SSE 流的协议细节，做工具调用审计时需绕开（R2 第 3 轮一手核验）。

**【落到 PRD 的动作】**
- §6「并发」行补「Web 层采用 Spring WebMVC（非 WebFlux）+ 虚拟线程」并指向 ADR-002；
- **新增 ADR-002**（与 ADR-001 同落 `docs/DECISIONS.md`）：「虚拟线程 WebMVC 的四条依据（技能匹配 / 场景匹配 / SSE 复用 / 叙事价值）+ WebFlux 评估放弃记录」；
- FR-TOOL-05 深度定义：最小版 = 1–2 个内置工具以 MCP Server 暴露（StreamableHttpMcpTransport）+ 装配期工具名归一化；实现顺序为先定工具执行器 SPI、MCP 只是暴露 adapter；超 5 天即降 roadmap；
- §8 排期落位：MCP 最小版随 M2（P3 工具执行器）交付，工作量 ≤5 天计入。

## 8. 演示场景：工单替身 + 对账修复做主角

**【裁决】** 演示主场景 = AI Agent 自动建工单（断网重放后工单数 == 1 终态断言）；**退款单不做**（资金语义自挖坑），README 写明「同一套幂等 / 补偿机制适用于退款等资金操作，工单是零资金风险的演示替身」。把退款式对账过程（补偿任务扫出脏数据并自动修复）做成演示主角 / 录屏。

**【理由】** 退款自带资金语义，会引来金额校验、部分退款、冲正、账户状态等资金安全追问，个人项目没有真实支付通道，等于自挖坑；懂得用替身控制风险在面试里反而是加分项（R1）；对账修复过程是「承认边界 → 证明可恢复」叙事的最强演示载体，也是与「换库回避问题」的分界线（R1/R3）。

**【落到 PRD 的动作】**
- FR-TOOL-04 故障注入用例升格为**主演示场景**（README 第一屏 / 一键演示 GIF 均用它）；
- §10 Out of Scope **新增**「退款 / 支付类资金语义演示（用工单替身替代，README 说明适用性）」；
- §4.1 对账链路（Outbox → 幂等消费 → 死信 → 补偿 → 对账 → 不一致清单）标注为演示主线；§12 结论表 P1 行与之呼应；
- **新增**：README 演示章节结构（工单终态断言 + 对账修复录屏 + 「替身适用性」说明）。

## 9. 边界声明：README 第一屏新增两条

**【裁决】** README 第一屏在五条确定性承诺之外，新增两条边界声明：① 本项目治理**数据面**，不承诺检索质量（召回率 / 引用准确率不在承诺范围）；② 一致性是**有 SLO 的可对账**，不是绝对一致。

## 15. P2 检索隔离：可见集租户必须与运行时 `TenantContext` 交叉校验

**【裁决】** `RetrievalService.search` 在计算之外**必须**校验 `visible.tenantId() == TenantContext.requireTenantIdAsLong()`，不一致即拒绝（403 + 审计）。同时 `t_kb_acl` / `t_doc_acl` 的 `tenant_id` 由**组合外键**绑定到被引用对象的属主租户。

**【理由】** 可见集是**值对象**，任何调用方都能 `new VisibilitySet(别的租户, …)`——ArchUnit 只能守护「签名含 VisibilitySet」，守护不了**来源**。另有跨租户**拒绝**向量：一行「租户 B 写、指向租户 A 的 kb_id」的 DENY 会遮蔽租户 A 的用户并凭 `UNIQUE(kb_id,user_id)` 占掉其 ACL 槽位（应用层补 `tenant_id` 条件 + DB 补组合外键，双防线）。

**【落到文档的动作】**
- ADR-008 修订段（已落）；
- PRD §9 `t_kb_acl` / `t_doc_acl` 行补「租户一致性由组合外键保证」；
- 「租户谓词承重性」进 CI：新增用例证明「去掉 `meta->>'tenantId'` 谓词后外租户 docId 可命中」，

## 16. P3 工具副作用：幂等指纹必须保精度；补偿的「成功」必须有受影响行数为证

**【裁决】** 三条：① 共享 ObjectMapper 开 `USE_BIG_DECIMAL_FOR_FLOATS`（幂等指纹的正确性前提）；② `ToolExecutor.compensate` 返回 `int`（受影响行数），`0` 记 `NO_OP` 而非 `SUCCEEDED`；③ 补偿失败可重跑（`PENDING ∪ FAILED(attempt < 上限)`），超上限单列 `exhausted`。

**【理由】** ① 默认 Jackson 把 JSON 小数降为 `Double`，两个仅在 17 位有效数字之后不同的输入得到**同一指纹** → 第二次调用静默重放首次结果（实测复现；`readTree` 同为 `DoubleNode`，救不了）；② 原 `void compensate` + 「没抛异常即成功」会产生「审计 SUCCEEDED、计数器 +1，而数据库什么都没变」的假成功；③ 原执行集合只查 `PENDING`，一次补偿失败即永久卡在「半补偿」，与 SPI 承诺的「等待人工/重跑」矛盾。三条同属 §4 归纳的「不报错、只是静默不生效」。

**【落到文档的动作】**
- ADR-009 修订段（已落）；`CompensationRunResponse` 增 `noOp` / `exhausted`；
- PRD §5.5 FR-TOOL-02 验收标准补「补偿成功以受影响行数为证；失败可重跑，超上限可观测」；
- 幂等键长度上收到入口（越界 400）并由迁移放宽列宽——PRD §9 `t_tool_invocation` 行补注。

## 17. P4a 配额：配额账本的键必须带租户；释放是「删键 + 回退」而不是 `settle(0)`

**【裁决】** ① `aiwarden:quota:reserve:{tenant}:{requestKey}`（结算键同）——**键一律带租户**；② `release` 语义由「`settle(0)`」变更为**独立脚本**（回退用量并删除预扣键与结算标记，且对已结算者 no-op）；③ 预算管理接口校验路径租户 == 调用方租户。

**【理由】** ① DB 唯一约束是 `(tenant_id, idem_key)`，两租户**可以**持有同一 idemKey；键不带租户时租户 B 命中租户 A 的预扣走幂等分支 → 「允许且不扣减」= 免费调用（实测复现：修前租户 2 的 usage 恒为空）；② `settle(0)` 只写标记不删键，导致释放后重试**完全不计费**（usage 恒 0 而明细有行）；③ `BillingController` 原先调 `requireTenantIdAsLong()` 却**丢弃返回值**，租户 A 可读写任意租户预算（改大即解除限流）。

**【落到文档的动作】**
- ADR-010 修订段（已落）；
- PRD §5.6 FR-COST-05 的「与厂商账单文件对账」改为**如实口径**：当前实现是「Redis 配额账 vs 自家明细表」，

## 20. M3 编排与评测口径：Mock 模型替身 + 真实治理管道（双轨机制先行、fixture 待录）

**【裁决】** ① M3 问答编排采用「确定性管线 + Mock 模型替身」：除模型生成由替身供货外，链路每一步都走 M1/M2 真实组件（可见集 / 下推检索 / 幂等与配额 / 计量 / 审计）；**评测验证的分层口径** = 验证「治理管道对任意模型决策的约束执行 100% 正确」，**不验证**「真实模型会不会做出该决策」（属 B1 检索质量 / 模型行为域，不在承诺范围）。② 双轨机制（Mock + 录制回放：`RecordingModelClient` 装饰器 / `ReplayModelClient` / JSON fixture）随 M3 落地，fixture 的真实模型录制待可用端点后补——**如实标注「机制就绪、fixture 待录」，不伪造数据**。③ 会话口径：M3 为「单轮问答 + 会话标识」，多轮上下文与 Checkpoint（`t_agent_session` / `t_agent_step`，P5）归 M4；④ 评测资产落点：样本 + 断言引擎在 `aiwarden-eval/src/main`，全栈门禁驱动在 `aiwarden-start/src/test`（与 20 条越权样本同落点），结论写 `t_eval_report`（V9 迁移，评测报告页数据源）。⑤ 携带裁决 19 的三项范围结论（P4b 砍除 / 用量看板自绘 / 限流已随 M2 交付）。

**【理由】** 无真实模型端点时，「Mock 返回固定文本」会让评测退化为**断言替身自己写的答案**（循环论证）——必须先钉死「验证什么（治理约束执行）与不验证什么（模型是否上当）」的分层口径，评测数字才有意义；与 P3 故障注入用例同构：注入的是「危险决策」，断言的是「治理拦住了它」。录制回放轨若伪造 fixture 即违背 §12 诚实原则，故「机制先行、fixture 如实待录」。

## 21. M3 收官口径：评测门禁结论进 PRD §12；前后端验证口径与 Maven 生命周期分离

**【裁决】**
① **评测结论按实测回填**：M3 门禁口径为 **24 条样本**（非「20–30 条」的区间表述），结论
`total=24 passed=24 denyBlocked=7/7 duplicateTickets=0 p95=52ms avgCost=0.000509 元`
进 PRD §12 结论表与 README 结论表；**P95 标注为逐轮抖动值**（首轮 44ms / 本轮 52ms，nearest-rank、样本量 24），
成本标注**演示单价口径**。样本数由 20–30 收敛到 24 = 实际交付值，属口径级变更。
② **前后端验证口径与 Maven 生命周期分离**：`aiwarden-web/` 是独立 pnpm 工程，
**不进 `mvn verify`、不计入测试数**（112 仍为 Java 侧口径）；其验证口径是
`pnpm build`（含 `vue-tsc --noEmit` 类型检查）+ dev server 冒烟（写入 `aiwarden-web/README.md`），
**该口径必须与 Java 侧测试数分开陈述，不得混算**。
③ **新增「启动冒烟」为依赖变更后的必要验证**：因 test scope 依赖降级曾导致「112 测试全绿但 `java -jar` 起不来」
（见 ADR-012 修订段缺陷 1），凡改依赖（尤其 scope）后必须补
`mvn -pl aiwarden-start -am package -DskipTests` + `java -jar` 启动冒烟。此条已入 `AGENTS.md` §4。
④ **人工确认开关维持缺省关闭**：`aiwarden.agent.tools.require-approval` 缺省为空（C 端确认卡片默认不出现），
演示时显式传 `-Daiwarden.agent.tools.require-approval=create_ticket` 打开；**不改缺省值**——
默认开启会让「建单」主演示动作多一次人工停顿，而该路径已有容器测试覆盖。

**【理由】** 「20–30 条」是设计目标区间，落地后实际是 24 条；结论表要能复现，就必须写实际值，
否则读者无法核对（与 §12 诚实原则一致）。前端不在 Maven 生命周期内是**有意设计**（避免 pnpm 成为 CI 硬依赖），
但必须显式说明「所以 CI 绿 ≠ 前端可构建」，否则又是一个「不报错但不生效」的盲区。缺陷 1 与缺陷 2（见 ADR-012）
都是「全绿但失效」形态，故把「启动冒烟」升为**必要验证步骤**而不是可选项。
